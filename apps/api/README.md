# @nd/api

The HTTP API: accounts (Better Auth), charger search and listings, host onboarding, bookings and payments, and the background jobs behind them. Fastify 5 with Zod schemas for every request and response; the OpenAPI 3.1 document is generated from them and served at `/openapi.json`.

## Running locally

```sh
pnpm db:up                         # Postgres with PostGIS on localhost:54320
pnpm db:migrate && pnpm db:seed
export DATABASE_URL=postgres://nd:nd@localhost:54320/nd
export AUTH_SECRET=$(openssl rand -hex 32)
export GATEWAY_INTERNAL_SECRET=$(openssl rand -hex 32)   # the same value the gateway uses
export CORS_ORIGINS=http://localhost:5173
pnpm --filter @nd/api dev          # http://localhost:3000
```

With the default console senders, sign-in links and phone codes are written to the console in development. To sign in with curl:

```sh
curl -X POST localhost:3000/auth/sign-in/magic-link -H 'content-type: application/json' \
  -H 'origin: http://localhost:5173' -d '{"email":"dev@example.com"}'
# open the link printed in the API's console; it sets the session cookie
```

`node dist/migrate.js` (or `pnpm --filter @nd/api migrate` from source) applies pending migrations and exits; the Docker image runs it as a one-off container before an upgrade.

## How it fits together

- `src/app.ts` builds the app from injected dependencies (`src/deps.ts`): the database, a clock, an id generator, email and SMS senders, Stripe Connect, `ChargerControl` (the gateway's commands, typed by the `@nd/domain` contract; `main.ts` uses its HTTP client) and the charger event subscription. Tests pass fakes.
- **Auth** (`src/auth/`): Better Auth at `/auth/*` on the Drizzle adapter, with its `user` model mapped onto `users` and its sessions, accounts and verifications in the `auth_*` tables. Magic links last 15 minutes and work once; phone codes verify the signed-in user's number and never sign anyone in. Sessions are httpOnly cookies for 30 days, renewed daily while used, and revocable through Better Auth's sign-out and session routes. One `onRequest` hook resolves the session; `requireUser` and `requireVerifiedPhone` guard routes.
- **Search and listings** (`src/routes/chargers.ts`): search uses `searchChargers` from `@nd/db`, which never returns exact positions. A listing shows free slots for the next 7 days, from availability rules in the charger's time zone minus bookings that hold the charger. The address and exact position are shown only to a driver with a confirmed, arrived or active booking there.
- **Host onboarding** (`src/routes/hosts.ts`): `POST /hosts {country}` creates the Stripe account in that country (IE or GB) and fixes the host's currency (EUR or GBP); every availability rule the host saves is priced in it, so bookings, charges and refunds follow. A serial registered to another live host is refused (409); a deleted host's tombstoned charger does not block its next owner. Only the Zappi v2.1 (serial starting with 2) and GLO can connect. The OCPP password is 20 random characters, returned once and stored as an argon2id PHC string by `hashChargerSecret` from `@nd/db`, the helper the gateway verifies it with. The onboarding long-poll subscribes to `LISTEN charger_events`, then re-reads the charger on every event (parsed with the versioned `@nd/domain` contract; anything else is skipped) and after a reconnect, because NOTIFY is not durable.
- **Bookings** (`src/routes/bookings.ts`, rules in `src/bookings/`): `POST /bookings` checks the charger is online and listed, the slot lies inside one availability window in the charger's time zone and under the host's daily cap, and refuses an overlap with 409 before calling Stripe. The price comes from `quote()` in `@nd/domain` (the slot's minutes at the hourly price, no fee) and is paid upfront. The host's daily cap is checked under a transaction-scoped advisory lock on the host, in the same transaction as the insert, so concurrent bookings cannot exceed it. A driver may have at most 3 requests waiting and make `BOOKING_RATE_LIMIT_PER_HOUR` bookings an hour. Instant book confirms at once with a 20-character idTag and charges the card; otherwise the price is held on the card and the host approves (`/approve`: idTag issued, hold captured; 402 if it has lapsed) or declines (`/decline`: hold released); a request expires 24 hours after it was made, or at the slot start if sooner. `/cancel` refunds by the rules in `cancellationRefund`: a driver before the host's cutoff (default 2 hours) gets everything back, after it nothing; a host cancelling refunds everything; never once the driver has arrived. The driver sees the address only while the booking holds the slot.
- **Payments** (`src/stripe/payments.ts`, `src/payments/`, `src/bookings/resume.ts`): destination charges, paid upfront (docs/adr/0005-pay-upfront.md). Each driver gets a Stripe Customer the first time they save a card (`POST /me/payment-methods/setup-intent`); the app confirms the SetupIntent with Stripe's SDK, so card details never reach the API. A booking is one off-session PaymentIntent with `transfer_data.destination` the host's connected account and `application_fee_amount` the platform fee plus the card fee passed on to the host (`chargeSplit` in `@nd/domain`); automatic capture for an instant booking, manual for a request. Refunds (`refundPayment`, `sendRefund`) always reverse the host's share and the application fee. Every change claims the booking's status first, recording any refund it owes in the same transaction (`updateBookingWithRefund`), then calls Stripe with one idempotency key per logical action (`booking-<id>-charge`, `-capture`, `-release`, `refund-<refund id>`). A call Stripe did not answer is recorded on the row and finished by the `resume-payment` job with the same key; the minute sweep queues it for anything left half way. Arriving, starting and the gateway's idTag check all need the payment `paid`.
- **Webhooks** (`src/routes/webhooks.ts`): `POST /webhooks/stripe` verifies the signature against the raw body, records the event id in `stripe_webhook_events` in the same transaction as its effects (a redelivery answers `duplicate`), and handles `payment_intent.succeeded`, `.canceled` and `.payment_failed` (recorded on the payment), `charge.refunded` (confirms pending refunds), `charge.dispute.created` and `.closed` (a card dispute recorded for support), `setup_intent.succeeded` (the first card becomes the default) and `account.updated` (mirrored into `hosts.payout_status`, which unblocks publishing). A webhook never moves money. Only event ids and types are logged.
- **Session control** (`src/routes/bookings-session.ts`, `src/sessions/`): the driver checks in with `POST /bookings/:id/arrive` (a paid booking, from `ARRIVAL_LEAD_MINUTES`, 4 hours by default, before the slot until it ends; an optional position's distance from the charger is recorded, never enforced), then `POST /bookings/:id/start` creates a `starting` session and sends `remoteStart` through `ChargerControl`. The gateway turns StartTransaction into `charging` and StopTransaction into `stopped`; this side only sends commands and marks failed starts (`sessions.stop_reason` holds the failure code; `@nd/domain` has the copy the app shows). A start rejected while the charger reports a transaction open is soft-reset and retried once by a job. Starting before the slot (the driver plugged in early), or with a `startAt` inside it, schedules the remote start for the slot start (or `startAt`) and records the plug-in in `bookings.plugged_in_at`; waiting is never billed. `POST /bookings/:id/stop` sends `remoteStop`; it changes nothing about what was paid. `GET /bookings/:id/session` is the live state for the driver or host.
- **Realtime** (`src/realtime/`): `GET /ws` (`@fastify/websocket`), authenticated by the session cookie, with the origin checked against `CORS_ORIGINS`, at most 5 connections per user, a ping every 30 s, a session re-check every 5 minutes and slow clients dropped. The feed takes every charger event from the one `LISTEN charger_events` connection (`subscribeAll`) and the API's own changes, re-reads the rows and pushes `booking:update`, `session:update` and `charger:status` to the users entitled to them; `resync` after the listener reconnects. The message schemas are in `@nd/domain` (`realtime.ts`); docs/ARCHITECTURE.md (section 9.1) describes them.
- **Email and SMS** (`src/senders/`): SMTP (nodemailer) or Resend for email and Twilio's REST API for SMS, chosen by the environment; the console senders stay for development and tests. End-to-end test stacks use the `capture` senders instead, which keep messages in memory for `GET /e2e/messages?to=…` (`src/routes/e2e.ts`); both exist only with `E2E_TEST_HOOKS=true`, which the environment schema and `buildApp` refuse in production, and the route is left out of the OpenAPI document. Each attempt times out after 10 seconds; server errors, rate limits and network failures are retried twice with backoff (SMTP: temporary 4xx replies), and Resend gets one idempotency key per message. A failure is a `MessageDeliveryError` naming the provider and a masked recipient (`a***@example.com`, `***567`); provider messages, which can echo the address or number, are never passed on. The templates (`templates.ts`) have a plain-text part and a simple HTML part with no images, remote resources or tracking.
- **Tax details** (`src/routes/tax-details.ts`, `src/tax/`): `PUT /hosts/me/tax-details` takes a host's legal name and date of birth, or company name and number, with address, tax country and TIN. The TIN is checked with `checkTin` from `@nd/domain` (IE: PPSN or tax reference with its check letter; UK: 10-digit UTR or National Insurance number). The TIN and date of birth are sealed with AES-256-GCM under the first key of `TAX_ENCRYPTION_KEYS`, with the host and column as associated data, and the key id is stored in the row. Reads never decrypt: the TIN comes back masked to its last three characters and the date of birth not at all. Saving sets `hosts.tax_details_complete`, which publishing a listing needs. Request bodies are never logged, and `tin` and `dateOfBirth` are on the log redaction list.
- **Account deletion** (`src/routes/account-deletion.ts`, `src/accounts/`): `POST /me/delete` refuses (409, with reasons) while the user has a booking that is not finished, as driver or host, or a payment or refund is still going through. Otherwise it records the request, due in 7 days, takes the user's chargers off the listings, emails an undo link to `PUBLIC_APP_URL/account/restore?token=…` (only the token's hash is stored) and then deletes every session, so the old cookie is 401 at once. Signing in again is refused (`ACCOUNT_DELETION_PENDING`) until the user undoes it with `POST /me/delete/cancel {token}`, which relists the chargers. When the request falls due, the `account-deletions` job anonymises the account: the `users` row stays as a tombstone (`deleted_at`, no name, email, phone, image or Stripe customer); linked sign-ins, sessions, codes and device tokens are deleted; vehicle plates and review comments are cleared; the driver's Stripe Customer is deleted (a failure leaves the request for the next run); a host who was paid keeps their tax details, still encrypted, with `retain_until` set `TAX_RECORD_RETENTION_YEARS` ahead (the `telemetry-retention` job purges them after it), and one never paid loses them at once; their chargers lose their address, OCPP password and exact position. Bookings, sessions, payments, refunds, reviews and disputes keep pointing at the tombstone, so accounting still adds up.
- **Retention** (`src/compliance/retention.ts`): the `telemetry-retention` job deletes meter values older than 24 months and calls `purge_ocpp_messages()` for the OCPP log; sessions and accounting rows are kept. The function runs as its owner; if the API connects as another role, grant that role `EXECUTE` on it.
- **Charger events** (`src/events/dispatcher.ts`): one `LISTEN charger_events` connection feeds every handler (`dispatchChargerEvents`); handlers only queue jobs, and on `resync` (after a reconnect) catch up from the tables.
- **Settlement** (`src/settlement/`, `src/routes/receipts.ts`, `src/routes/host-sessions.ts`, `src/routes/admin.ts`): the booking was paid upfront, so closing a session moves no money. A `session_stopped` event queues `reconcile-session`, which checks the meter delta against the last MeterValue (within 0.2 kWh) and records the kWh (`reconciled`), or flags the session `needs_review` with its `review_reason` for support. A session still open after its slot (plus `STALE_SESSION_GRACE_MINUTES`) is closed from its last MeterValue as `reconciled`, or `needs_review` without one. A booking still `arrived` after its slot with no session that started is closed too: `completed` and refunded in full automatically when a start was tried, the car plugged in or the charger is not online (the charger let the driver down); otherwise a `no_show`, not refunded. The minute sweep also re-queues request expiries and no-shows whose jobs went missing, and payments to resume. Settlement jobs push `booking:update` and `session:update` through the realtime feed. Support refunds a paid booking in full or in part with `POST /admin/bookings/:id/refund {amountCents?, note}` (users in `ADMIN_USER_IDS`), never more than is left. `GET /bookings/:id/receipt` shows the driver or host the price paid, refunds, and the session as evidence (start and stop, kWh with meter start and stop, meter readings and power samples), the card (driver) or the gross, card fee and net (host); `POST /bookings/:id/review` lets the driver rate a completed booking once, and listings average the ratings. `POST /bookings/:id/dispute` (`src/bookings/dispute.ts`) lets the driver of a completed, cancelled or no-show booking raise a dispute for support, one open at a time; it records the dispute and moves no money. `POST /hosts/chargers/:id/stop` is the host's emergency stop: the session charging on their charger gets `RemoteStopTransaction` through `ChargerControl` (404 for anyone else's charger, 409 with nothing charging), and closes when the charger reports the stop.
- **Push notifications** (`src/push/`, `src/notifications/`, `src/routes/devices.ts`): `POST /me/devices` registers an FCM token (iOS and Android) or a web push subscription (its endpoint must be https on a browser push service: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com` or `*.push.apple.com`, checked again before each send so the API never posts to an address a client chose), `DELETE /me/devices/:id` forgets it on sign-out, and each account keeps its 10 most recently seen devices. `GET`/`PATCH /me/notification-preferences` are the user's switches, all on until turned off. Booking, session and settlement code queues a `notify` job for each event (`queueNotification`, which never fails the change that caused it); the charger-event dispatcher queues session start and stop, faults and offline spells (checked again 10 minutes later, so a charger back by then is not reported). The job decides who hears what (`rules.ts`): the host hears of requests and new bookings, arrivals, session start, session end with what the guest paid and what the host keeps after card fees once the session is reconciled (or without it 15 minutes after the stop, if it is not), charger offline and faults (once per 30 minutes); the driver hears of approvals, declines, expiries, cancellations, and charging starting, stopping or failing to start. A ledger (`notifications`, unique per event and user) sends each one once across retries; tokens the provider rejects are forgotten. Pushes carry the kind and ids only, never names or addresses.
- **Host dashboard** (`src/routes/hosts-dashboard.ts`, `src/data/dashboard.ts`): `GET /hosts/dashboard` answers this month's earnings (what drivers paid less refunds, the card fees passed on, and what the host keeps), finished sessions and kWh, 8 weekly points, a card per charger (status pill, listing switch, next booking), tonight's bookings and pending requests; `GET /hosts/calendar` lists bookings by day, 30 days by default (at most 31). Periods are in the time zone of the host's first charger, and a booking counts in the period its slot starts in.
- Data access lives in `src/data/`; unit tests mock it, integration tests run it against Postgres.
- Errors are `application/problem+json` (`src/http/problem.ts`), including Better Auth's, which keep its `code` and `message`.

## Jobs

Background jobs run inside the API process on [pg-boss](https://github.com/timgit/pg-boss), in its own `pgboss` schema of the same database: no Redis and no separate worker. `buildApp` starts them when the app is ready (installing or migrating the schema) and stops them when it closes, letting running jobs finish for up to 8 seconds.

A job is a typed definition (`src/jobs/jobs.ts`):

```ts
export const noShowJob = defineJob({
  name: "booking-no-show", // the queue
  payload: z.object({ bookingId: z.uuid() }), // validated on send and on run
  retry: { limit: 5, delaySeconds: 60, backoff: true, maxDelaySeconds: 3600 },
  run: ({ bookingId }, services: Services, attempt) => markNoShow(services, bookingId),
});

await services.jobs.send(noShowJob, { bookingId }, { startAfter, singletonKey: bookingId });
```

- Add the definition to the list `buildApp` starts (`BOOKING_JOBS` in `src/bookings/jobs.ts`, or a list of your own next to it).
- Each queue uses pg-boss's `stately` policy: while a job with a singleton key is queued, retrying or running, sending another with the same key does nothing. Use the id the job is about as the key. A job sent without a key gets a random one.
- A handler throws to fail an attempt; it is retried with exponential backoff until `retry.limit`, and `attempt.lastAttempt` tells it when no retry follows. Handlers must be safe to run twice: check the row's state before acting.
- A payload that fails validation is logged and dropped, never retried.
- Tests: `runner.runNow(job, payload)` runs a handler at once as its last attempt; `runner.drain()` works every ready job, including ones they queue. Unit tests use the in-memory runner in `test/fakes.ts`.

| Job                       | When                                              | What                                                                                                 |
| ------------------------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `booking-expire-request`  | 24 h after a request, or its slot start if sooner | Cancels a request the host never answered and releases the hold                                      |
| `booking-no-show`         | slot end + 15 min                                 | A confirmed booking never arrived at becomes `no_show`; not refunded                                 |
| `resume-payment`          | a Stripe call left unanswered (sweep)             | Finishes a charge, capture, release or refund with the same idempotency key                          |
| `account-deletions`       | daily, 03:15 UTC                                  | Anonymises accounts whose 7-day undo window has passed (`processDueDeletions`)                       |
| `telemetry-retention`     | daily, 03:45 UTC                                  | Deletes meter values and OCPP messages older than 24 months, and tax details past their retention    |
| `reconcile-session`       | `session_stopped`, sweep                          | Checks the meter and records the kWh                                                                 |
| `close-stale-session`     | slot end + 10 min (sweep)                         | Closes a session with no StopTransaction from its last MeterValue                                    |
| `close-arrived-booking`   | slot end + 10 min (sweep)                         | Closes an arrival with no session: refunded if the charger let the driver down, otherwise a no-show  |
| `settlement-sweep`        | every minute                                      | Queues whatever is due: sessions to close, missing lifecycle jobs, payments to resume                |
| `session-remote-start`    | a scheduled start time, or 20 s after a reset     | Sends the remote start; a retry after a reset is the only one                                        |
| `session-start-timeout`   | 120 s after an accepted remote start              | No StartTransaction: the start fails and the charger is asked for a StatusNotification               |
| `session-window-end-stop` | slot end + 5 min                                  | Sends a remote stop to a session still running; gives up a start still pending                       |
| `notify`                  | a booking, session or charger event               | Pushes the notifications it leads to, once per recipient; retries when every device failed retryably |
| `notifications-prune`     | daily, 04:30 UTC                                  | Forgets sent-notification records older than 90 days                                                 |

A definition with a `cron` (five fields, UTC) is also scheduled; pg-boss keeps one schedule per job, and the runner drops it when the field goes. The plain functions behind the jobs are exported from `src/scheduled.ts`. `node dist/rotate-tax-keys.js` re-encrypts tax details still on an older key (see docs/RUNBOOK.md).

## Tests

```sh
pnpm --filter @nd/api test                 # unit tests with coverage; no database
docker run -d --name stripe-mock -p 127.0.0.1:12111:12111 stripe/stripe-mock:v0.206.0
DATABASE_URL=postgres://nd:nd@localhost:54320/nd pnpm --filter @nd/api test:integration
```

Integration tests create and drop their own database per file. Payments run against [stripe-mock](https://github.com/stripe/stripe-mock) at `STRIPE_API_BASE_URL` (default `http://localhost:12111`), which checks every request against Stripe's API but keeps no state; `test/stripe-mock.ts` applies Stripe's documented state changes on top (an off-session confirm makes the intent `succeeded`, or `requires_capture` with manual capture; capture makes it `succeeded`; refunds count against what was received) and can decline the next charge. `src/__snapshots__/openapi.json` is the committed API contract: a change to a route's schema fails the unit tests until the snapshot is updated (`pnpm --filter @nd/api exec vitest run -u`), so contract changes show up in review. The test writes it in Prettier style, so formatting the file never changes it.
