# @nd/api

The HTTP API: accounts (Better Auth), charger search and listings, host onboarding, bookings and payments, and the background jobs behind them. Fastify 5 with Zod schemas for every request and response; the OpenAPI 3.1 document is generated from them and served at `/openapi.json`.

## Running locally

```sh
pnpm db:up                         # Postgres with PostGIS on localhost:54320
pnpm db:migrate && pnpm db:seed
export DATABASE_URL=postgres://nd:nd@localhost:54320/nd
export AUTH_SECRET=$(openssl rand -hex 32)
export GATEWAY_INTERNAL_SECRET=$(openssl rand -hex 32)   # the same value the gateway uses
export CORS_ORIGINS=http://localhost:5173
pnpm --filter @nd/api dev          # http://localhost:3000
```

With the default console senders, sign-in links and phone codes are written to the console in development. To sign in with curl:

```sh
curl -X POST localhost:3000/auth/sign-in/magic-link -H 'content-type: application/json' \
  -H 'origin: http://localhost:5173' -d '{"email":"dev@example.com"}'
# open the link printed in the API's console; it sets the session cookie
```

`node dist/migrate.js` (or `pnpm --filter @nd/api migrate` from source) applies pending migrations and exits; the Docker image runs it as a one-off container before an upgrade.

## How it fits together

- `src/app.ts` builds the app from injected dependencies (`src/deps.ts`): the database, a clock, an id generator, email and SMS senders, Stripe Connect, `ChargerControl` (the gateway's commands, typed by the `@nd/domain` contract; `main.ts` uses its HTTP client) and the charger event subscription. Tests pass fakes.
- **Auth** (`src/auth/`): Better Auth at `/auth/*` on the Drizzle adapter, with its `user` model mapped onto `users` and its sessions, accounts and verifications in the `auth_*` tables. Magic links last 15 minutes and work once; phone codes verify the signed-in user's number and never sign anyone in. Sessions are httpOnly cookies for 30 days, renewed daily while used, and revocable through Better Auth's sign-out and session routes. One `onRequest` hook resolves the session; `requireUser` and `requireVerifiedPhone` guard routes.
- **Search and listings** (`src/routes/chargers.ts`): search uses `searchChargers` from `@nd/db`, which never returns exact positions. A listing shows free slots for the next 7 days, from availability rules in the charger's time zone minus bookings that hold the charger. The address and exact position are shown only to a driver with a confirmed, arrived or active booking there.
- **Host onboarding** (`src/routes/hosts.ts`): `POST /hosts {country}` creates the Stripe account in that country (IE or GB) and fixes the host's currency (EUR or GBP); every availability rule the host saves is priced in it, so bookings, PaymentIntents and transfers follow. A serial registered to another live host is refused (409); a deleted host's tombstoned charger does not block its next owner. Only the Zappi v2.1 (serial starting with 2) and GLO can connect. The OCPP password is 20 random characters, returned once and stored as an argon2id PHC string by `hashChargerSecret` from `@nd/db`, the helper the gateway verifies it with. The onboarding long-poll subscribes to `LISTEN charger_events`, then re-reads the charger on every event (parsed with the versioned `@nd/domain` contract; anything else is skipped) and after a reconnect, because NOTIFY is not durable.
- **Bookings** (`src/routes/bookings.ts`, rules in `src/bookings/`): `POST /bookings` checks the charger is online and listed, the slot lies inside one availability window in the charger's time zone and under the host's daily cap, and refuses an overlap with 409 before calling Stripe. The quote comes from `quote()` in `@nd/domain` (the slot's minutes at the hourly price, no fee). Instant book confirms at once with a 20-character idTag; otherwise the host approves (`/approve`, idTag issued then) or declines (`/decline`, authorisation released). `/cancel` applies the host's cutoff (default 2 hours): free before it, one hour at the hourly price (capped at the quote) after it, never once the driver has arrived. The driver sees the address only while the booking holds the slot.
- **Payments** (`src/stripe/payments.ts`, `src/payments/`): separate charges and transfers. Each driver gets a Stripe Customer the first time they save a card (`POST /me/payment-methods/setup-intent`); the app confirms the SetupIntent with Stripe's SDK, so card details never reach the API. A slot starting within 6 days is authorised at booking with an off-session, manual-capture PaymentIntent on the platform account (`transfer_group` = booking id); a later one keeps the saved card (`card_saved`) and is authorised by a job 24 hours ahead. `captureForBooking(bookingId, amount)` captures at most the authorised amount; `createHostTransfer(paymentId)` sends the capture less the platform fee to the host's connected account with `source_transaction`, or records it as held while the session needs review, a dispute is open, the host's tax details are incomplete or payouts are not enabled. Every Stripe write has an idempotency key derived from the booking (`booking-<id>-authorise`, `-release`, `-capture`, `-transfer`). Stripe errors reach clients only as a 502 `payment-provider-error`.
- **Webhooks** (`src/routes/webhooks.ts`): `POST /webhooks/stripe` verifies the signature against the raw body, records the event id in `stripe_webhook_events` in the same transaction as its effects (a redelivery answers `duplicate`), and handles `payment_intent.amount_capturable_updated`, `.succeeded`, `.canceled` and `.payment_failed`, `setup_intent.succeeded` (the first card becomes the default) and `account.updated` (mirrored into `hosts.payout_status`, which unblocks publishing; once payouts are enabled, held transfers are retried). Only event ids and types are logged.
- **Session control** (`src/routes/bookings-session.ts`, `src/sessions/`): the driver checks in with `POST /bookings/:id/arrive` (from 15 minutes before the slot until it ends; an optional position's distance from the charger is recorded, never enforced), then `POST /bookings/:id/start` creates a `starting` session and sends `remoteStart` through `ChargerControl`. The gateway turns StartTransaction into `charging` and StopTransaction into `stopped`; this side only sends commands and marks failed starts (`sessions.stop_reason` holds the failure code; `@nd/domain` has the copy the app shows). A start rejected while the charger reports a transaction open is soft-reset and retried once by a job. An optional `startAt` inside the slot schedules the remote start (the night-rate hook) and records the plug-in in `bookings.plugged_in_at`, from which billing then runs. `POST /bookings/:id/stop` sends `remoteStop`; nothing is captured here. `GET /bookings/:id/session` is the live state for the driver or host.
- **Realtime** (`src/realtime/`): `GET /ws` (`@fastify/websocket`), authenticated by the session cookie, with the origin checked against `CORS_ORIGINS`, at most 5 connections per user, a ping every 30 s, a session re-check every 5 minutes and slow clients dropped. The feed takes every charger event from the one `LISTEN charger_events` connection (`subscribeAll`) and the API's own changes, re-reads the rows and pushes `booking:update`, `session:update` and `charger:status` to the users entitled to them; `resync` after the listener reconnects. The message schemas are in `@nd/domain` (`realtime.ts`); docs/ARCHITECTURE.md (section 9.1) describes them.
- **Email and SMS** (`src/senders/`): SMTP (nodemailer) or Resend for email and Twilio's REST API for SMS, chosen by the environment; the console senders stay for development and tests. End-to-end test stacks use the `capture` senders instead, which keep messages in memory for `GET /e2e/messages?to=…` (`src/routes/e2e.ts`); both exist only with `E2E_TEST_HOOKS=true`, which the environment schema and `buildApp` refuse in production, and the route is left out of the OpenAPI document. Each attempt times out after 10 seconds; server errors, rate limits and network failures are retried twice with backoff (SMTP: temporary 4xx replies), and Resend gets one idempotency key per message. A failure is a `MessageDeliveryError` naming the provider and a masked recipient (`a***@example.com`, `***567`); provider messages, which can echo the address or number, are never passed on. The templates (`templates.ts`) have a plain-text part and a simple HTML part with no images, remote resources or tracking.
- **Tax details** (`src/routes/tax-details.ts`, `src/tax/`): `PUT /hosts/me/tax-details` takes a host's legal name and date of birth, or company name and number, with address, tax country and TIN. The TIN is checked with `checkTin` from `@nd/domain` (IE: PPSN or tax reference with its check letter; UK: 10-digit UTR or National Insurance number). The TIN and date of birth are sealed with AES-256-GCM under the first key of `TAX_ENCRYPTION_KEYS`, with the host and column as associated data, and the key id is stored in the row. Reads never decrypt: the TIN comes back masked to its last three characters and the date of birth not at all. Saving sets `hosts.tax_details_complete` and re-queues transfers held only for it. Request bodies are never logged, and `tin` and `dateOfBirth` are on the log redaction list.
- **Account deletion** (`src/routes/account-deletion.ts`, `src/accounts/`): `POST /me/delete` refuses (409, with reasons) while the user has a booking that is not finished, as driver or host, or owes a payment. Otherwise it records the request, due in 7 days, takes the user's chargers off the listings, emails an undo link to `PUBLIC_APP_URL/account/restore?token=…` (only the token's hash is stored) and then deletes every session, so the old cookie is 401 at once. Signing in again is refused (`ACCOUNT_DELETION_PENDING`) until the user undoes it with `POST /me/delete/cancel {token}`, which relists the chargers. When the request falls due, the `account-deletions` job anonymises the account: the `users` row stays as a tombstone (`deleted_at`, no name, email, phone, image or Stripe customer); linked sign-ins, sessions, codes and device tokens are deleted; vehicle plates and review comments are cleared; the host's tax details are deleted and their chargers lose their address, OCPP password and exact position. Bookings, sessions, payments, transfers, reviews and disputes keep pointing at the tombstone, so accounting still adds up.
- **Retention** (`src/compliance/retention.ts`): the `telemetry-retention` job deletes meter values older than 24 months and calls `purge_ocpp_messages()` for the OCPP log; sessions and accounting rows are kept. The function runs as its owner; if the API connects as another role, grant that role `EXECUTE` on it.
- **Charger events** (`src/events/dispatcher.ts`): one `LISTEN charger_events` connection feeds every handler (`dispatchChargerEvents`); handlers only queue jobs, and on `resync` (after a reconnect) catch up from the tables.
- **Settlement** (`src/settlement/`, `src/routes/receipts.ts`, `src/routes/host-sessions.ts`, `src/routes/admin.ts`): a `session_stopped` event queues `reconcile-session`. It checks the meter delta against the last MeterValue (within 0.2 kWh), captures `billedAmount` from `@nd/domain` (from `billingStart`, the plug-in time of a scheduled start or else StartTransaction, to stop, rounded up to 5 minutes, capped at the quote), records the platform fee, marks the session `reconciled` and creates the host's transfer, which is held while tax details are incomplete or payouts are off. A disagreement, a missing authorisation or a capture that keeps failing moves the session to `needs_review` with its `review_reason`, captures nothing and logs a warning for support. Every step moves rows forward only from the state it expects and Stripe calls carry idempotency keys, so a re-run never captures or transfers twice. A session still open 10 minutes after its slot is closed from its last MeterValue as `needs_host_confirmation`, both sides are emailed, and it is billed once the host confirms (`POST /hosts/sessions/:id/confirm`) or 72 hours pass; the host may dispute instead (`POST /hosts/sessions/:id/dispute`), which records a dispute and leaves it for support. A booking still `arrived` 10 minutes after its slot with no session that started is closed too: `completed` with nothing billed (the authorisation released) when a start was tried or the car plugged in, since the failure may be the charger's; otherwise the driver never plugged in and the no-show rule applies (one hour, capped at the quote, paid to the host). Settlement jobs push `booking:update` and `session:update` through the realtime feed when they change a booking or session. Support settles a session in review with `POST /admin/sessions/:id/resolve {amountCents}` (users in `ADMIN_USER_IDS`), which also resolves the booking's open disputes. `GET /bookings/:id/receipt` shows the driver or host the time billed, the breakdown (cap and fee lines only when they apply), kWh with meter start and stop, the effective price per kWh, the card (driver) or payout (host); `POST /bookings/:id/review` lets the driver rate a completed booking once, and listings average the ratings. `POST /bookings/:id/dispute` (`src/bookings/dispute.ts`) lets the driver of a completed, cancelled or no-show booking raise a dispute for support, one open at a time; it records the dispute and moves no money. `POST /hosts/chargers/:id/stop` is the host's emergency stop: the session charging on their charger gets `RemoteStopTransaction` through `ChargerControl` (404 for anyone else's charger, 409 with nothing charging), and closes when the charger reports the stop.
- **Push notifications** (`src/push/`, `src/notifications/`, `src/routes/devices.ts`): `POST /me/devices` registers an FCM token (iOS and Android) or a web push subscription (its endpoint must be https on a browser push service: `fcm.googleapis.com`, `updates.push.services.mozilla.com`, `*.notify.windows.com` or `*.push.apple.com`, checked again before each send so the API never posts to an address a client chose), `DELETE /me/devices/:id` forgets it on sign-out, and each account keeps its 10 most recently seen devices. `GET`/`PATCH /me/notification-preferences` are the user's switches, all on until turned off. Booking, session and settlement code queues a `notify` job for each event (`queueNotification`, which never fails the change that caused it); the charger-event dispatcher queues session start and stop, faults and offline spells (checked again 10 minutes later, so a charger back by then is not reported). The job decides who hears what (`rules.ts`): the host hears of requests and new bookings, arrivals, session start, session end with the amount billed and their share once settlement captured it (or without it 15 minutes after the stop, if settlement has not), charger offline and faults (once per 30 minutes); the driver hears of approvals, declines, expiries, cancellations, and charging starting, stopping or failing to start. A ledger (`notifications`, unique per event and user) sends each one once across retries; tokens the provider rejects are forgotten. Pushes carry the kind and ids only, never names or addresses.
- **Host dashboard** (`src/routes/hosts-dashboard.ts`, `src/data/dashboard.ts`): `GET /hosts/dashboard` answers this month's earnings (the host's share of captured payments, transferred or not), finished sessions and kWh, 8 weekly points, a card per charger (status pill, listing switch, next booking), tonight's bookings and pending requests; `GET /hosts/calendar` lists bookings by day, 30 days by default (at most 31). Periods are in the time zone of the host's first charger, and a booking counts in the period its slot starts in.
- Data access lives in `src/data/`; unit tests mock it, integration tests run it against Postgres.
- Errors are `application/problem+json` (`src/http/problem.ts`), including Better Auth's, which keep its `code` and `message`.

## Jobs

Background jobs run inside the API process on [pg-boss](https://github.com/timgit/pg-boss), in its own `pgboss` schema of the same database: no Redis and no separate worker. `buildApp` starts them when the app is ready (installing or migrating the schema) and stops them when it closes, letting running jobs finish for up to 8 seconds.

A job is a typed definition (`src/jobs/jobs.ts`):

```ts
export const noShowJob = defineJob({
  name: "booking-no-show", // the queue
  payload: z.object({ bookingId: z.uuid() }), // validated on send and on run
  retry: { limit: 5, delaySeconds: 60, backoff: true, maxDelaySeconds: 3600 },
  run: ({ bookingId }, services: Services, attempt) => markNoShow(services, bookingId),
});

await services.jobs.send(noShowJob, { bookingId }, { startAfter, singletonKey: bookingId });
```

- Add the definition to the list `buildApp` starts (`BOOKING_JOBS` in `src/bookings/jobs.ts`, or a list of your own next to it).
- Each queue uses pg-boss's `stately` policy: while a job with a singleton key is queued, retrying or running, sending another with the same key does nothing. Use the id the job is about as the key. A job sent without a key gets a random one.
- A handler throws to fail an attempt; it is retried with exponential backoff until `retry.limit`, and `attempt.lastAttempt` tells it when no retry follows. Handlers must be safe to run twice: check the row's state before acting.
- A payload that fails validation is logged and dropped, never retried.
- Tests: `runner.runNow(job, payload)` runs a handler at once as its last attempt; `runner.drain()` works every ready job, including ones they queue. Unit tests use the in-memory runner in `test/fakes.ts`.

| Job                            | When                                               | What                                                                                                         |
| ------------------------------ | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `authorise-booking`            | 24 h before the slot                               | Authorises the saved card; retries a decline, then cancels the booking at no charge                          |
| `booking-expire-request`       | slot start                                         | Cancels a request the host never answered and releases the authorisation                                     |
| `booking-no-show`              | slot end + 15 min                                  | A confirmed booking never arrived at becomes `no_show` and pays one hour (capped at quote)                   |
| `host-transfer`                | after a fee is captured, or tax details are saved  | Sends or holds the host's transfer                                                                           |
| `account-deletions`            | daily, 03:15 UTC                                   | Anonymises accounts whose 7-day undo window has passed (`processDueDeletions`)                               |
| `telemetry-retention`          | daily, 03:45 UTC                                   | Deletes meter values and OCPP messages older than 24 months (`purgeExpiredTelemetry`)                        |
| `reconcile-session`            | `session_stopped`, host confirmation, sweep        | Checks the meter, captures the billed amount, creates the host's transfer                                    |
| `close-stale-session`          | slot end + 10 min (sweep)                          | Closes a session with no StopTransaction from its last MeterValue; emails both sides                         |
| `close-arrived-booking`        | slot end + 10 min (sweep)                          | Closes an arrival with no session: completed if a start was tried or the car plugged in, otherwise a no-show |
| `session-confirmation-timeout` | 72 h after closing                                 | Bills a closed session the host has not answered                                                             |
| `release-held-transfers`       | payouts enabled, review or dispute settled (sweep) | Retries held transfers whose hold has cleared                                                                |
| `settlement-sweep`             | every minute                                       | Queues whatever settlement work is due, in case an event was missed                                          |
| `weekly-payout-summary`        | Fridays, 09:00 UTC                                 | Queues a `host-payout-summary` email per host with sessions or held transfers                                |
| `host-payout-summary`          | from the weekly job                                | Emails one host the week's sessions, amounts and held transfers with why                                     |
| `session-remote-start`         | a scheduled start time, or 20 s after a reset      | Sends the remote start; a retry after a reset is the only one                                                |
| `session-start-timeout`        | 120 s after an accepted remote start               | No StartTransaction: the start fails and the charger is asked for a StatusNotification                       |
| `session-window-end-stop`      | slot end + 5 min                                   | Sends a remote stop to a session still running; gives up a start still pending                               |
| `notify`                       | a booking, session or charger event                | Pushes the notifications it leads to, once per recipient; retries when every device failed retryably         |
| `notifications-prune`          | daily, 04:30 UTC                                   | Forgets sent-notification records older than 90 days                                                         |

A definition with a `cron` (five fields, UTC) is also scheduled; pg-boss keeps one schedule per job, and the runner drops it when the field goes. The plain functions behind the jobs are exported from `src/scheduled.ts`. `node dist/rotate-tax-keys.js` re-encrypts tax details still on an older key (see docs/RUNBOOK.md).

## Tests

```sh
pnpm --filter @nd/api test                 # unit tests with coverage; no database
docker run -d --name stripe-mock -p 127.0.0.1:12111:12111 stripe/stripe-mock:v0.206.0
DATABASE_URL=postgres://nd:nd@localhost:54320/nd pnpm --filter @nd/api test:integration
```

Integration tests create and drop their own database per file. Payments run against [stripe-mock](https://github.com/stripe/stripe-mock) at `STRIPE_API_BASE_URL` (default `http://localhost:12111`), which checks every request against Stripe's API but keeps no state; `test/stripe-mock.ts` applies Stripe's documented state changes on top (an off-session manual-capture confirm leaves the intent `requires_capture`, capture makes it `succeeded`) and can decline the next authorisation. `src/__snapshots__/openapi.json` is the committed API contract: a change to a route's schema fails the unit tests until the snapshot is updated (`pnpm --filter @nd/api exec vitest run -u`), so contract changes show up in review. The test writes it in Prettier style, so formatting the file never changes it.
